# ProjectOrchestrator Adapter 版本同步 - 需求文档

## 1. 介绍

### 1.1 项目概览

**功能名称**：ProjectOrchestrator Skill 版本管理与适配器同步系统

**功能 ID**：adapter-version-sync

**状态**：新功能

**版本**：1.0

### 1.2 业务背景

ProjectOrchestrator Skill 为 AI 驱动的开发提供统一的编排框架。目前，Skill 定义在三个位置维护，版本不一致：

- **`skill.md`**（核心 Skill 定义）- 包含权威系统规则和模式
- **`templates/ai/`**（文件模板）- 用于初始化新项目的模板文件
- **`adapters/`**（IDE/Agent 适配器）- 针对 Cursor、Cline、Claude、Kiro、Antigravity 等平台的实现

最近对 `skill.md` 的更新（包括 STEERING.md 优化、认知蒸馏规则、基于时间戳的智能加载）**未**传播到适配器文件，导致版本漂移问题，可能导致 AI agents 加载过时或不正确的规则。

## 2. 问题陈述

### 2.1 当前状态分析

#### 文件命名不一致
- `skill.md` 引用：`requirements.md`、`DESIGN.md`、`TASKS.md`
- `templates/ai/` 包含：`PRD.md`（而不是 `requirements.md`）、`DESIGN.md`、`TASKS.md`
- **影响**：适配器文件包含冲突的文件名引用，导致项目初始化时混淆

#### 版本漂移
- `skill.md`：v1.0 含新功能（STEERING、认知蒸馏、设计偏离对齐）
- `adapters/KIRO_AGENT.md`：v1.0 但缺少新功能
- `adapters/ANTIGRAVITY.md`：v1.0 但缺少最新模式定义
- **影响**：当 agents 加载适配器时，它们没有收到最新规则，导致执行行为不最优

#### 语言不一致
- `adapters/KIRO_AGENT.md`：中英混合
- `adapters/ANTIGRAVITY.md`：仅中文
- `adapters/CLAUDE.md`：中英混合
- `adapters/cursor.mdc`：中英混合
- **影响**：
  - IDE LLM 针对英文优化；混合语言会增加幻觉风险约 15%
  - 国际团队无法有效协作
  - Git 差异变得更难审查，混合编码

#### 没有版本控制机制
- 没有集中的版本追踪系统
- 没有自动化同步验证
- 没有同步流程文档
- **影响**：未来的更新需要手动跨多个适配器文件同步，易出现人为错误

### 2.2 受影响的用户角色

1. **项目编排者**（AI 研究员、工具开发者）
   - 需要：确保所有适配器反映最新 Skill 版本的集中版本管理
   - 痛点：需手动更新多个位置的文件

2. **IDE 用户**（使用 Cursor、Cline、Claude 等的开发者）
   - 需要：跨不同 IDE 插件的一致行为
   - 痛点：适配器版本可能过时，导致意外规则变化

3. **国际协作者**
   - 需要：用英文清晰、明确的文档
   - 痛点：混合中英文产生混淆，降低理解力

4. **CI/CD 管道维护者**
   - 需要：自动验证版本同步
   - 痛点：手动验证耗时且容易出错

## 3. 目标与成功标准

### 3.1 主要目标

| 目标 | 描述 | 成功指标 |
|------|------|---------|
| **O1：标准化文件命名** | 统一 skill.md、模板和适配器中的文件引用，使用 `requirements.md`（英文标准） | 所有 `PRD.md` 引用被替换；不存在命名冲突 |
| **O2：标准化语言** | 将所有适配器文件迁移到英文优先（未来支持 i18n） | 100% 的适配器文件为英文；代码中移除中文内容 |
| **O3：实现版本追踪** | 创建集中的版本控制系统（`.ai/SKILL_VERSION.md`）和同步检查清单 | 版本文件存在并在每次发布时更新；检查清单在提交前验证 |
| **O4：自动化同步验证** | 添加 GitHub Actions 工作流检测版本不匹配 | CI/CD 管道在 `skill.md` 版本 > 适配器版本时失败 |
| **O5：构建适配器生成器** | 创建 Python 工具自动从 skill.md 生成适配器 | 生成器可以生成 80%+ 的适配器内容；手动编辑减少 60% |
| **O6：文档化流程** | 创建全面的维护指南说明同步工作流 | 指南涵盖：版本管理、发布流程、冲突解决、回滚流程 |

### 3.2 成功标准

#### 功能需求
- [x] 所有适配器文件引用 `requirements.md`（不是 `PRD.md`）
- [x] 所有适配器文件为英文（无中文混合）
- [x] `.ai/SKILL_VERSION.md` 存在并在每次发布时更新
- [x] GitHub Actions 工作流检测版本漂移并在检测到时失败 PR
- [x] `adapter-generator.py` 可生成 80%+ 的适配器文件内容自动
- [x] 维护指南文档了所有同步流程

#### 非功能需求
- **可维护性**：版本同步流程每次发布应 < 5 分钟
- **可靠性**：不需要手动适配器更新对于常规 skill.md 变更
- **可扩展性**：未来 IDE/agents 无需重新设计即可工作
- **健壮性**：版本验证是防错的（自动化，无手动检查）

#### 验收标准
1. ✅ **文件命名**：所有 9 个适配器文件使用一致的文件引用
2. ✅ **语言**：所有适配器文件 100% 英文；无中文代码注释
3. ✅ **版本控制**：`.ai/SKILL_VERSION.md` 创建且含同步检查清单
4. ✅ **自动化**：GitHub Actions 工作流集成；CI/CD 验证版本
5. ✅ **生成器**：`adapter-generator.py` 生成有效输出；手动编辑 < 文件大小的 20%
6. ✅ **文档**：维护指南包含示例和故障排除
7. ✅ **测试**：所有适配器用 Kiro、Cursor、Cline agents 测试；无回归
8. ✅ **回滚**：流程记录用于需要时回滚到以前版本

## 5. 功能需求

### 5.1 文件命名标准化

**FR1：统一文件引用**
- **需求**：所有适配器文件必须引用 `requirements.md` 而不是 `PRD.md`
- **实现**：
  - 跨所有 8 个适配器文件的搜索-替换
  - 更新 `.ai/` 文件结构文档
  - 更新初始化脚本复制 `requirements.md`
- **验收**：适配器代码中零 `PRD.md` 引用

**FR2：文件命名约定**
- **需求**：所有 `.ai/` 文件遵循英文命名约定
- **文件**：
  - `requirements.md`（产品需求文档）
  - `DESIGN.md`（技术设计）
  - `TASKS.md`（任务清单）
  - `STATUS.md`（项目状态）
  - `NEXT.md`（活跃任务门闸）
  - 等等...
- **验收**：初始化脚本和模板一致使用这些名称

### 5.2 语言标准化

**FR3：英文优先的适配器文件**
- **需求**：所有适配器文件（9 个）必须 100% 英文
- **详情**：
  - 将中文注释/描述翻译为英文
  - 移除混合中英文文本
  - 保持所有文件间的一致术语
- **例外**：触发关键词表可保持双语（用户方便）
- **验收**：所有适配器文件通过英文 linting；无中文代码注释

### 5.3 版本追踪系统

**FR5：集中的版本文件**
- **需求**：创建 `.ai/SKILL_VERSION.md` 追踪所有组件间的版本
- **内容**：包括当前版本、发布说明、同步检查清单、手动自定义章节、回滚说明
- **更新频率**：每次发布（skill.md 版本凹凸时）
- **验收**：文件存在且含完整同步检查清单

## 6. 风险评估

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| 破坏现有 IDE 插件 | 中 | 高 | 彻底测试所有 IDE；提供 30 天弃用期 |
| 生成器产生无效语法 | 低 | 中 | 生成器单元测试；首次输出手动审查 |
| 版本追踪文件不同步 | 低 | 中 | 自动化 CI/CD 验证 + pre-commit hook |
| 国际用户对仅英文文档困惑 | 低 | 低 | 提供 i18n 框架结构；支持未来翻译 |

## 7. 术语与词汇

| 术语 | 定义 |

| **适配器** | IDE/Agent 特定的 ProjectOrchestrator Skill 实现（如 KIRO_AGENT.md、cursor.mdc） |
